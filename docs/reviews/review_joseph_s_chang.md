# Review: Spectacles: A Verified Compiler from Semiring-Weighted Automata to Zero-Knowledge Scoring Circuits

**Reviewer:** Joseph S. Chang (Automated Reasoning and Logic)
**Score: 8/10**

---

The formal architecture of Spectacles is admirably rigorous in its treatment of the specification-to-circuit pipeline. The key contribution from an automated reasoning perspective is the recognition that the gap between "this program ran correctly" (what existing ZK systems prove) and "this program computes the intended function" (what Spectacles proves) is precisely the specification problem that has plagued verified compilation since the CompCert era. By choosing weighted finite automata as the intermediate representation, the system inherits decidable equivalence from classical automata theory (Schützenberger 1961; Berstel & Reutenauer 2011) while providing a clean algebraic target for circuit synthesis. The two-tier soundness architecture is particularly well-designed from a proof-theoretic perspective: Tier 1's generic algebraic compilation, where the soundness theorem `circuit_sound_algebraic` is proved once and instantiated per embeddable semiring, demonstrates exactly the kind of parametric reasoning that modern proof assistants excel at. The injective semiring homomorphisms ι: S → 𝔽_p for counting and Boolean semirings are mathematically straightforward but their mechanization in Lean 4 with `Matrix`-based transitions is non-trivial and constitutes genuine proof engineering. The Tier 2 gadget-assisted approach for the tropical semiring, where min is encoded via bit-decomposition comparison gadgets, correctly identifies that this is a fundamentally different proof obligation requiring per-semiring argument.

The automated reasoning contributions—specifically the `kleene_dec` and `wfa_equiv` tactics—deserve close scrutiny. The `kleene_dec` tactic, which decides equational Kleene-algebra goals via reduction to NFA equivalence, is well-grounded in the decidability of the equational theory of Kleene algebras (Kozen 1994). However, the use of `native_decide` bounded to WFAs with ≤ 20 states raises a fundamental question about the tactic's utility: real-world metric specifications may produce automata with hundreds of states (the proposal lists state counts up to ~1,100 for a 512-token input), and the tactic cannot handle these cases. The fallback to `sorry`-with-documentation for larger instances means that in practice, the automated reasoning capability is limited to toy examples and small components. The `wfa_equiv` tactic, based on minimization via the weighted Myhill-Nerode quotient followed by isomorphism checking, is more broadly applicable but its completeness proof is explicitly deferred. This creates an asymmetry: the tactic can produce a "not equivalent" verdict with a distinguishing word (which is self-certifying), but a "equivalent" verdict relies on the unproven correctness of the minimization procedure. For a system that claims to eliminate trust in unverified implementations, this is a meaningful gap.

The certificate checking architecture is sound in its overall design but raises questions about the trusted computing base (TCB). The STARK verifier is the ultimate trust anchor: if it accepts a proof, the score is correct. But the verifier itself is a Rust implementation (~24K–28K LoC for the circuit synthesizer subsystem alone), and its correctness is established by the Lean 4 theorems, not by the Rust code directly. The connection between the Lean 4 formalization and the Rust implementation is maintained by differential testing (100K random pairs), not by verified extraction or a refinement proof. This is a well-known gap in verified systems (the "DeepSpec gap"), and the proposal is honest about it, but it means the end-to-end guarantee has a trust boundary at the Lean-to-Rust interface. The EvalSpec DSL compiler (15K–18K LoC in Rust) translates typed specifications to WFAs, and its correctness is established by the `eval_equiv_wfa` theorem in Lean 4—but again, the theorem applies to the Lean formalization, not the Rust implementation. The proposal's evaluation plan correctly addresses this via differential testing, which is the pragmatic state-of-the-art, but the automated reasoning community should note that "verified compiler" here means "compiler with a verified specification and extensive testing," not "compiler extracted from a proof." The PSI contamination detector's trie-structured optimization (O((n₁ + n₂) · λ) communication) is a clean algorithmic contribution, and the composition security argument via Canetti's sequential composition theorem is standard but correctly applied. Overall, this is a strong contribution that correctly identifies and solves a real specification problem, with honest scoping and appropriate use of formal methods.
